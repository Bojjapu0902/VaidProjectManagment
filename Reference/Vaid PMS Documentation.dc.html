04

Lifecycle stages — the default template

Stages run in sequence and each one ends at a client decision. A stage cannot advance until the client has approved it, and a rejection sends the work back into the same stage with the revision counter incremented. This single rule shapes the dashboard, the timeline and both approval screens.

!
The eight stages below are the studio's default template, not a fixed structure

Stages differ from project to project — an interior fit-out has no statutory submission, a masterplan needs two, and a small residential job may merge concept and preliminary design. So the lifecycle is defined per project when the project is created (SCR-05, step 3): the admin or PM starts from a template, then renames, reorders, adds, removes and dates the stages, and marks which of them require a client approval gate. The default template is editable in settings (SCR-16); changing it affects new projects only.

Purpose

Stand up a project, its client and its lifecycle in one pass. Five steps rather than one long form, because the budget and document steps are often filled by a different person hours later; the draft persists between them.

Why step 3 exists

Stages differ from project to project, so the lifecycle cannot be hardcoded. This step is where a project gets its own: pick a template, rename stages to the studio's language for that job, drag to reorder, remove what does not apply, add anything bespoke, set start and target dates, and decide which stages need the client to approve before work moves on. Everything downstream — the dashboard tracker, the client timeline, the approval gates, the reports — reads from what is set here, and all of it stays editable afterwards in Stage management (SCR-07), including any custom stage created here.

Components
<Stepper /><Input /><Select /><ClientPicker /><FileUpload /><StageBuilder /><TemplatePicker /><DateRangeRow />dnd-kit
GET /stage-templates · POST /projects with a stages[] array · zod schema per step
States & rules
· Code is generated server-side and cannot be edited· A new client triggers account creation and a welcome email· Status is set to NEW; the project's first stage opens with its checklist· A project needs at least two stages and at least one client gate to be created· Stage dates must run in sequence — the builder flags gaps and overlaps before continue· Removing a stage is non-destructive here; it can be restored until the project is saved· Stage colours come from the template; a custom stage picks from the eight system colours, never a free picker· The chosen template is recorded on the project, so reports can compare like with like· Steps validate on continue, not on blur, so a half-typed field never nags· Cancel discards the draft after a confirm dialog

Advance stage
Purpose

Where the team moves work forward and where the admin edits the lifecycle itself. Two jobs, one screen: the rail on the left owns the structure — reorder, add, remove, and select a stage — and the panel on the right edits the selected stage in place. The advance action is always visible but explains in words why it is unavailable, rather than silently disabling itself.

Editing a stage

Everything on the panel is editable by admin or the assigned PM: the stage name, its colour, its description, both dates, the client-gate and client-visibility switches, and the milestone list — where rows can be renamed, reassigned, re-dated, reordered and deleted inline. No modal, no separate form. Custom stages created at project setup are edited here identically to template ones and carry a CUSTOM tag in the rail, so a bespoke phase is a first-class stage rather than a note.

States & rules
· The stage list is this project's own, set at creation (SCR-05) and fully editable here — this screen is the canonical place to change it; SCR-06's edit panel links straight to it · A stage that holds documents or a recorded approval can be renamed, recoloured and re-dated but not removed — the remove button states the reason · Adding a stage inserts it after the one selected in the rail and renumbers the rest; client-visible numbering updates on their timeline immediately · Custom stages pick from the eight system colours, never a free picker, so the tracker stays legible · Moving a date warns how many later stages shift and offers to cascade them · Removing a stage with an open client approval is blocked until that approval is withdrawn · Turning a client gate on mid-project applies from the next advance, never retroactively · Future stages are locked for work; only the active stage takes uploads and milestone ticks· Advancing requires all milestones closed and, where the stage has a gate, client approval recorded· Reverting a stage is admin-only and asks for a reason, which is written to the audit trail· Percentage can be set manually or derived from milestones — the studio picks one in settings· Every save emits a notification to the client if the stage status changed

Approval workflow

The rule that connects five screens. Work is uploaded, checked internally, sent to the client, and either advances the stage or comes back as a revision. Nothing skips the internal check, and no gated stage advances without a recorded client decision. Which stages are gated is set per project at creation (SCR-05, step 3) — an ungated stage completes on the team's own sign-off.

01Admin or PM must review every document before it reaches the client.
